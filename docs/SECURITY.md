# Безопасность Gem Radar

Здесь записано, как злоумышленник мог бы атаковать приложение, что уже закрыто в коде и что владелец должен
настроить сам. Код проверен «глазами атакующего» по четырём направлениям: ключи владельца, деньги
пользователей, сервер и бот, сам сайт.

## Что нужно сделать владельцу (10 минут, один раз)

Самое ценное в проекте — **токен Telegram-бота**. С ним злоумышленник может прислать подписчикам кнопку на
поддельное мини-приложение, а хранилище Telegram привязано к боту, а не к сайту. Значит, такая подделка
прочитала бы ключи встроенных кошельков. Токен бота можно получить через GitHub или Cloudflare, поэтому
защищайте оба аккаунта.

1. **Двухфакторная защита (2FA)** — обязательно на GitHub, Cloudflare и в Telegram (Настройки →
   Конфиденциальность → Облачный пароль). Лучше приложение-аутентификатор или ключ, а не SMS.
2. **Ключи — только в GitHub Secrets.** Никогда не присылайте их в чат, почту или скриншоты и не
   коммитьте в код. Telegram-бот, Cloudflare и twitterapi.io никогда не попросят их у вас в переписке.
3. **Защита ветки `main`**: GitHub → Settings → Branches → Add branch ruleset → ветка `main` →
   *Restrict deletions*, *Block force pushes*, *Require a pull request before merging*. Так даже с
   украденным паролем нельзя тихо подменить код или адрес комиссии.
4. **Оповещения об уязвимостях**: Settings → Code security → включите *Dependabot alerts*, *Secret
   scanning* и *Push protection* (последнее не даст случайно закоммитить ключ).
5. **Чужие PR**: Settings → Actions → General → *Require approval for all external contributors*.
6. **Токен Cloudflare** — с узкими правами (см. `docs/SERVER_SETUP.md`, шаг 2.4) и по возможности со сроком
   действия.
7. **twitterapi.io** — пополняйте небольшими суммами. Сервер и так тратит не больше
   `DAILY_TWITTER_BUDGET` проверок в сутки.
8. **Не публикуйте другие сайты на GitHub Pages в этом же аккаунте**, а если публикуете — только свои и
   проверенные. Все они живут на одном адресе `<ник>.github.io` и делят общее хранилище браузера. Ключи
   кошелька там больше не хранятся (см. ниже), но портфель и настройки — да. Самое надёжное — свой домен
   для сайта (Settings → Pages → Custom domain).

### Если ключ утёк

| Что утекло | Что сделать сразу |
|---|---|
| Токен бота | @BotFather → `/revoke` → выберите бота → новый токен в секрет `TELEGRAM_BOT_TOKEN` → Actions → Deploy → Run workflow |
| Токен Cloudflare | Cloudflare → My Profile → API Tokens → *Roll* (или удалить и создать новый) → обновить секрет |
| Ключ twitterapi.io | Сгенерировать новый в кабинете twitterapi.io → обновить секрет `TWITTERAPI_KEY` |
| Пароль GitHub | Сменить пароль, проверить Settings → Sessions и SSH keys, затем пересоздать все секреты |
| Адрес комиссии | Новые адреса — в переменные `FEE_SOLANA_WALLET` / `FEE_EVM_WALLET` → Run workflow |

## Что уже закрыто в коде

### Деньги пользователей

- **Подмена сделки агрегатором.** Если API Jupiter, KyberSwap или LI.FI взломают или подменят ответ,
  приложение не подпишет вредную транзакцию (`src/lib/txGuard.ts`):
  - EVM: деньги и разрешение (approve) уходят только официальным роутерам KyberSwap и LI.FI, сумма
    транзакции не больше суммы сделки;
  - Solana: проверяется, кто платит комиссию сети, какие программы вызываются (Jupiter и служебные),
    куда переводится SOL (только на свой wSOL-счёт) и какие токен-инструкции есть (никаких переводов и
    разрешений на ваши токены). Есть и потолок приоритетной комиссии.
- **Разрешения (approve)** выдаются ровно на продаваемую сумму, не «бесконечные». Именно бесконечные
  разрешения опустошили кошельки при взломе контракта LI.FI в 2024 году.
- **Ключи встроенного кошелька** хранятся только в защищённом хранилище Telegram: Keychain / Keystore
  телефона или DeviceStorage. В `localStorage` браузера они больше не пишутся, потому что его видят другие
  сайты на `<ник>.github.io`. Старая копия оттуда переносится и стирается. Если хранилища Telegram нет
  (старая версия), кошелёк не создаётся.
- **Вывод средств** — только после окна подтверждения с полным адресом и суммой: вирусы подменяют адрес в
  буфере обмена. Показ ключей — тоже после предупреждения.
- **Подмена настроек.** Slippage ограничен 20%, Solana RPC принимается только по `https`, остальные значения
  берутся только из списка. Даже если чужой сайт на том же адресе изменит хранилище, сэндвич-атаки через
  огромный slippage не будет.

### Сайт

- **Политика безопасности контента (CSP)** в собранном сайте: скрипты — только свои, SDK Telegram и
  встроенный загрузчик по хэшу. Внедрённый скрипт браузер не выполнит (это проверяет автотест).
- **Ссылки и картинки из чужих данных** (DexScreener) — только `https`; React дополнительно блокирует
  `javascript:`-ссылки.
- Нигде нет `innerHTML`, `eval`, `dangerouslySetInnerHTML`.

### Сервер и бот

- **Вебхук бота** принимает только запросы с секретом, который знает Telegram. Сравнение идёт за
  постоянное время.
- **Лимит Twitter-проверок** нельзя выжечь: не больше 20 запросов в минуту с одного IP и 8 проверок в минуту
  из одного чата. Четверть дневного лимита всегда остаётся сканеру алертов. Браузерам разрешён только ваш
  сайт (CORS).
- Адреса проверяются по формату, монета должна существовать на DexScreener, тексты в сообщениях бота
  экранируются (нельзя вставить ссылку-ловушку в название токена).

### Публикация (GitHub Actions)

- Каждый секрет передаётся только тому шагу, которому он нужен. Установка пакетов, тесты и сборка ключей
  не видят.
- Пакеты ставятся с `--ignore-scripts`: заражённый пакет из npm не выполнит код при установке. Так
  устроены известные атаки на CI (например, червь Shai-Hulud 2025 года).
- Действия GitHub закреплены по коммиту, у токена GitHub — только чтение, право публикации есть лишь у
  последнего шага.
- Проверки PR из чужих форков идут без секретов.

## Известные ограничения

- Сайт статический: если злоумышленник получит доступ к вашему GitHub, он сможет изменить код. Поэтому
  важны 2FA и защита ветки `main` (см. выше).
- Встроенный кошелёк защищён хранилищем Telegram, но не паролем. Если украдут токен бота, поддельное
  мини-приложение сможет прочитать ключи пользователей. Защита — пункты 1–2 выше. Дополнительно можно
  включить PIN-код на кошелёк (в планах).
- `npm audit` показывает уязвимости в `braces`, `stream-json` и `uuid`. Они в инструментах сборки и в
  серверной части библиотек и в сайт не попадают. Это проверено по дереву зависимостей.
